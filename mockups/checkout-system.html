    The two tables that matter
    
  
    CREATE TABLE orders (
  id               uuid PRIMARY KEY,
  customer_id      uuid NOT NULL,
  status           text NOT NULL DEFAULT 'PENDING',
  idempotency_key  text NOT NULL UNIQUE,
  total_cents      bigint NOT NULL,
  created_at       timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE outbox (
  id          bigserial PRIMARY KEY,
  topic       text NOT NULL,
  payload     jsonb NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  sent_at     timestamptz
);
CREATE INDEX outbox_unsent ON outbox (id) WHERE sent_at IS NULL;
    
  
    Replicas serve status reads on a cache miss. Replication lag p99 is 40 ms, well inside the 30 s cache TTL.
    

    

    
  
    Topics
    
  
    
    
    TopicProducerConsumers
    
    
      
    order.placedoutbox relaypayment worker
    
      
    payment.capturedpayment workerorder service, notifications
    
      
    payment.failedpayment workerorder service, notifications
    
        
  
    
  
    All three are keyed by order id, so every event for one order lands on one partition, in order.
    

    

    
  
    Retry policy
    
  
      
    
    • 3 attempts, backoff 1 s then 4 s, each with a 3 s timeout.
      • 
    
    • The idempotency key is the order id, so attempt 3 can never create a second charge.
      • 
    
    • A hard decline is not retried. Only timeouts and 5xx are.
      •

    Cache-aside, in five lines
    
  
    func Status(id string) (Order, error) {
    if o, ok := cache.Get("order:" + id); ok { return o, nil }
    o, err := replica.GetOrder(id)
    if err == nil { cache.Set("order:"+id, o, 30*time.Second) }
    return o, err
}
    
  
    Every status change also deletes the key, so the 30 s TTL is a backstop, not the freshness guarantee.
    

    

    
  
    Rate limit
    
  
    Token bucket per customer id: 100 requests per second, burst 20. POST /orders has its own bucket of 5 per minute, which stops a stuck retry loop from creating a storm of orders.
    

    

    
  
    Why two lanes
    
  
    This connection carries traffic both ways. The order service publishes through the outbox relay and consumes payment results to confirm or cancel. Each direction is drawn as its own lane, so the motion never has to lie about direction.
    

    

    
  
    BEGIN;
INSERT INTO orders (id, customer_id, idempotency_key, total_cents)
  VALUES ($1, $2, $3, $4);
INSERT INTO outbox (topic, payload)
  VALUES ('order.placed', $5);
COMMIT;
    
  
    If either insert fails, both roll back, so an event can never describe an order that does not exist.
    

    

    
  
    Why 202, not 201
    
  
    The order exists but is not paid. 202 Accepted tells the client the work continues; the app shows "Order placed" and polls the status, which is the Check status flow.
    

    

    
  
    Worst case, in time
    
  
    Three attempts at a 3 s timeout, plus 1 s and 4 s of backoff, is 14 s before payment.failed. The customer left the checkout screen about 13.7 s earlier.
    

    

    
  
    SELECT id, topic, payload
  FROM outbox
 WHERE sent_at IS NULL
 ORDER BY id
 LIMIT 100
   FOR UPDATE SKIP LOCKED;
    
  
    SKIP LOCKED lets several relay replicas run without publishing the same row twice. A crash after publishing but before sent_at is set produces one duplicate, which consumers already ignore by order id.
    

    

    
  
    Idempotency
    
  
    The Idempotency-Key header is stored in orders.idempotency_key. A second request with the same key hits the unique index, and the handler returns the first order's 202 instead of creating another.
